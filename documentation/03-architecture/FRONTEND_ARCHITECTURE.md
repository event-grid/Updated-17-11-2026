# EVNTGRID — Frontend Architecture

| | |
|---|---|
| **Scope** | customer-web, provider-portal, admin-portal |
| **Stack (confirmed)** | Next.js, TypeScript, Tailwind CSS, shadcn/ui, TanStack Query, React Hook Form, Zod, Vitest, Playwright, Docker |
| **Status** | For owner review. Routes and features marked PROPOSED or DECISION are not confirmed requirements. |

## 1. Independence model

Each application has its own repository, dependencies, Tailwind configuration, shadcn/ui components, generated API client, Docker image and deployment (ADR-001, ADR-011). Nothing is imported between applications. Conventions below are repeated in each one by agreement, not by shared code.

| | customer-web | provider-portal | admin-portal |
|---|---|---|---|
| Hostname | www.evntgrid.com | partner.evntgrid.com | admin.evntgrid.com |
| API surfaces | public, customer | provider | admin |
| Rendering emphasis | Server-rendered public pages | Interactive, signed-in | Interactive, data-heavy |
| Search engine indexing | Public pages | No | No |
| Design intent | Discovery and trust | Productive daily work | Dense operational tools |

## 2. Application structure

The same internal layout is used in each app.

```text
public/                 Static files (generated by Next.js)
src/
  app/                  Next.js routes, layouts, loading and error boundaries
  components/ui/        shadcn/ui components copied into this app
  components/layout/    This app's navigation and page frames
  features/<feature>/   Screens, forms, query definitions for one feature
  hooks/                Shared React hooks
  lib/api/generated/    OpenAPI Generator output, never edited
  lib/api/client.ts     Base URL, credentials, CSRF, error mapping
  lib/query/            Query client, query key factory
  lib/server/           Server-only API access
  providers/            React context providers, such as the TanStack Query provider
  stores/               Kept EMPTY. No client-state library is approved (CD-23)
  types/                Shared TypeScript types that are not generated from the API
  config/               Public, non-secret configuration
tests/                  Vitest and Playwright
Dockerfile              Location undecided (U-30)
```

**Creation order (CD-21).** The folder script creates only `frontend/`. Each application is generated directly into `frontend/<application>` by `create-next-app`, and the folders above are added afterwards. `components/ui` and `lib/api/*` appear when shadcn/ui and OpenAPI Generator are first used.

**Client state (CD-23).** `stores/` stays empty. No client-state library is approved: no Zustand, Redux or similar. Server data lives in TanStack Query. Local UI state uses React's built-in state.

**Dockerfile (U-30).** The earlier design placed a Dockerfile in each application. The owner's folder plan also has `infrastructure/docker`. The location is undecided, and nothing is created until it is.

Dependency direction: `app` uses `features`; `features` use `components` and `lib`; `features` never import other features' internals.

## 3. Rendering and data flow

| Page type | Rendering | Data path |
|---|---|---|
| Public marketplace pages | Server Components, cached by the rules below | Public API without cookies |
| Signed-in lists and details | Server prefetch where useful, then client refresh | Server forwards session cookie; TanStack Query hydrates |
| Interactive screens | Client Components | Browser to the same-origin API |
| Forms and actions | Client Components | Browser to the same-origin API, with CSRF token |

**Caching rules**

- Only responses from the public API may be cached.
- Signed-in requests are never cached by Next.js or CloudFront.
- Server-only API code sits behind a `server-only` boundary.

**`proxy.ts`** handles optimistic redirects for a missing session cookie. It never decides access (AR-20). Server Actions are not used for business operations, since mutations go directly to the API.

## 4. Server state with TanStack Query

| Rule | Detail |
|---|---|
| Only source of server state | No server data in other stores or long-lived local state (CD-05). The owner confirmed that `stores/` stays empty and no client-state library is added (CD-23) |
| Query keys | Factory per feature: surface, resource, ID or filters |
| Filters | URL search parameters are the source of truth, and appear in query keys |
| Freshness | Refetch on focus and after related mutations (AR-09) |
| Polling | Only for visible screens that change often. Intervals are set during build |
| Mutations | Send an `Idempotency-Key` for protected actions. Optimistic updates are for low-risk actions only, such as marking a notification as read |
| Sign-out | Query cache is fully cleared |
| Conflict | On 409, refetch and tell the user that the record changed |

### Invalidation

| Successful action | Refresh |
|---|---|
| Add or edit plan item | Event plan |
| Submit enquiry | Enquiries list, event plan |
| Accept or decline quotation | Quotations, enquiry, bookings |
| Start or complete payment | Payment status, booking |
| Provider sends quotation | Provider enquiries, provider quotations |
| Admin approves or rejects provider | Provider queue, provider detail |

## 5. Forms

React Hook Form holds form state and Zod describes each form's input (TA-13 for the resolver).

| Concern | Rule |
|---|---|
| Purpose of Zod | Format, required fields, immediate feedback (ADR-010) |
| Not in Zod | Eligibility, approval, pricing, availability and any rule from `CUSTOMER_BUSINESS_RULES.md` |
| Backend errors | 422 field errors from the API are mapped onto form fields |
| Generated types | Zod's output must match the generated request type, checked by TypeScript |
| Secrets | Forms never collect card data; Razorpay Checkout does |

## 6. API client

OpenAPI Generator produces a `typescript-fetch` client per surface (`API_DESIGN.md`, section 7). `lib/api/client.ts` adds a same-origin base path, credentials, CSRF header, correlation ID and conversion of Problem Details into typed errors. Feature code uses the client and doesn't call `fetch` directly.

## 7. UI system and cross-cutting concerns

| Concern | Approach |
|---|---|
| Components | shadcn/ui copied into each app. Customised independently |
| Tables | shadcn/ui data table, which needs `@tanstack/react-table` (TA-13) |
| Styling | Tailwind tokens per app. A shared brand palette is agreed by convention |
| Allowed actions | A button appears only if the API's `allowedActions` lists it (AR-18) |
| Backend-supplied text | SR-2 messages and status labels are displayed as sent |
| Loading and errors | Route-level loading and error boundaries; empty states per list |
| Accessibility | Keyboard use, labels, contrast; target standard open (see gaps document) |
| Localisation | Structure text for later translation; languages under D-30 |
| Security headers | CSP per app, including Razorpay on customer-web |
| Environment | Only non-secret values use `NEXT_PUBLIC_` |
| Telemetry | OpenTelemetry on Next.js servers; correlation ID forwarded |
| Docker | Next.js standalone output in a minimal image |
